## Requirements
### Requirement: 管理员配置用户软透支额度

系统 MUST 允许管理员通过现有用户编辑能力为单个用户配置非负的余额软透支额度。未配置和配置为 `0` MUST 表示不额外允许透支，并保持该用户现有余额准入行为。

#### Scenario: 管理员设置透支额度
- **WHEN** 管理员将用户的允许超支额度设置为 `100`
- **THEN** 系统必须保存该用户的透支额度为 `100`
- **THEN** 后续余额计费请求必须按该用户的软透支线判断是否可以发起

#### Scenario: 默认额度保持兼容
- **WHEN** 存量用户没有显式配置透支额度
- **THEN** 系统必须将该用户的透支额度视为 `0`
- **THEN** 系统必须保持变更前的余额准入行为

#### Scenario: 清除透支额度
- **WHEN** 管理员将用户的允许超支额度改为 `0`
- **THEN** 系统必须停止允许该用户基于用户级额度继续透支

#### Scenario: 拒绝负额度
- **WHEN** 管理员提交小于 `0` 的允许超支额度
- **THEN** 系统必须拒绝该更新
- **THEN** 系统不得改变用户原有的透支额度

### Requirement: 余额模式按软透支线准入

系统 MUST 在余额计费模式下使用当前余额、用户透支额度和现有 minimum balance reserve 共同判断请求准入。用户余额尚未到达有效软透支线时 MUST 允许发起请求，达到或低于不含 reserve 的透支线时 MUST 按余额不足拒绝新请求。

#### Scenario: 正余额用户保持可用
- **WHEN** 用户透支额度为 `0` 且当前余额满足现有 minimum balance reserve
- **THEN** 系统必须允许该余额计费请求继续

#### Scenario: 零额度用户保持现有拒绝行为
- **WHEN** 用户透支额度为 `0` 且当前余额不满足现有余额准入条件
- **THEN** 系统必须按余额不足拒绝新请求

#### Scenario: 透支额度内允许请求
- **WHEN** 用户透支额度为 `100`
- **AND** 用户当前余额为 `-80`
- **AND** 其他请求资格检查均通过
- **THEN** 系统必须允许该余额计费请求继续

#### Scenario: 到达透支线拒绝请求
- **WHEN** 用户透支额度为 `100`
- **AND** 用户当前余额为 `-100`
- **THEN** 系统必须按余额不足拒绝新请求

#### Scenario: 最后一次请求越过软透支线
- **WHEN** 请求开始时用户余额尚未到达有效软透支线
- **AND** 请求完成后的实际费用使余额低于该透支线
- **THEN** 系统必须记录完整的实际费用并允许余额低于该透支线
- **THEN** 系统必须拒绝该用户之后的新余额计费请求

#### Scenario: 并发在途请求越过软透支线
- **WHEN** 多个余额计费请求在用户到达软透支线前并发通过准入
- **THEN** 系统必须分别按实际费用结算这些已在途请求
- **THEN** 系统不得把软透支额度宣称或处理为并发下的严格信用硬上限

### Requirement: 各余额准入层一致执行额度

API Key 鉴权预检和 billing cache 预检 MUST 使用同一用户透支额度语义。管理员修改额度后，系统 MUST 失效受影响用户的认证快照，使后续新请求读取更新后的配置。

#### Scenario: 负余额用户通过两层准入
- **WHEN** 用户当前余额仍在其透支额度内
- **THEN** API Key 鉴权预检不得仅因余额小于或等于 `0` 而拒绝请求
- **THEN** billing cache 预检必须使用相同用户额度继续判断

#### Scenario: 降低额度及时生效
- **WHEN** 管理员把负余额用户的透支额度降低到当前余额已经达到的范围
- **THEN** 系统必须失效该用户现有 API Key 认证快照
- **THEN** 后续新请求必须按新的较低额度被拒绝

#### Scenario: 提高额度及时生效
- **WHEN** 管理员提高因余额不足而被拒绝用户的透支额度
- **THEN** 系统必须失效该用户现有 API Key 认证快照
- **THEN** 后续新请求必须按新的较高额度重新判断

### Requirement: 已知金额的余额预占不得越过透支线

当系统在请求执行前已经知道需要冻结的余额金额时，系统 MUST 通过原子数据库条件保证预占后的可用余额不低于用户透支线。

#### Scenario: 批量图片预占位于额度内
- **WHEN** 用户透支额度为 `100`、当前余额为 `-80` 且批量图片需要预占 `15`
- **THEN** 系统必须原子地允许预占
- **THEN** 预占后的余额必须为 `-95`

#### Scenario: 批量图片预占将越过额度
- **WHEN** 用户透支额度为 `100`、当前余额为 `-80` 且批量图片需要预占 `25`
- **THEN** 系统必须拒绝该预占并返回余额不足
- **THEN** 系统不得改变用户的 balance 或 frozen balance

### Requirement: 非余额计费限制保持不变

用户软透支额度 MUST 只影响余额计费资格和余额预占，不得改变订阅用量限制、API Key 独立额度、用户平台额度、请求计价或最终 usage 扣费金额。

#### Scenario: 订阅请求不使用透支额度
- **WHEN** 请求使用有效订阅计费
- **THEN** 系统必须继续按订阅状态和订阅用量限制判断资格
- **THEN** 用户透支额度不得扩大订阅限额

#### Scenario: API Key 独立额度仍然生效
- **WHEN** 用户仍在透支额度内但 API Key 独立额度已耗尽
- **THEN** 系统必须继续按 API Key 额度耗尽拒绝请求

#### Scenario: 最终扣费口径保持不变
- **WHEN** 使用透支额度放行的请求完成
- **THEN** 系统必须继续使用现有最终 actual cost 扣减用户余额并记录 usage

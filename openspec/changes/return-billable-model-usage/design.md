## 设计原则

一次请求或 WebSocket 一轮使用固定的计量策略快照。上游 usage 保持独立，完成与计费一致的缓存分类、相关上游用量合并后，通过现有 BuildBillableUsage 生成计费用量；费用计算、持久化与用户响应采用相同策略和口径。后台任务必须显式传递快照。

协议输出保留未知字段，遵守协议的总量与明细关系：OpenAI 输入包含缓存，Anthropic 普通输入不包含缓存；Gemini 输出包含候选和思考用量。缓存写入、缓存读取及对应 TTL 明细维持现有计费规则，不应整体乘倍率。字段的拆分必须保证总量与计费一致，并避免因分项独立向上取整导致总和错误。Embeddings 不使用该倍率。

SSE 在已解析事件处输出计费用量，保持事件顺序、累计/增量语义及 flush 行为；WebSocket 按每轮隔离策略和用量。禁止将响应中的计费用量重新作为原始用量计费。兼容桥接若产生额外上游调用，响应需使用与结算相同的合并用量和取整顺序。

普通响应仅在完整用量可得时保证与计算出的账单用量一致。断连、上游缺少 usage、失败事件或入账失败时，响应不得伪造完整结果；现有异步结算可能在客户端已收到响应后失败，标准 usage 本身不是扣费成功凭证。按次、图片数量和其他非 token 费用无法完整表达于 token usage。

生成请求开始前读取设置；读取失败时中止上游调用，避免把临时错误固定为倍率 1。WebSocket 建连时为首轮读取，后续轮在转发前重新读取；每轮的快照随原始用量传入后台计费任务。缓存分类和额外上游用量在放大前确定。

## 验证

按协议覆盖非流式、流式、WebSocket、兼容转换、缓存和小数倍率取整，比较上游原始数据、响应标准 usage、持久化 billable 字段和计费输入；覆盖配置热更新、特殊缓存归类、多上游用量、缺失 usage、错误、断连和重复入账。保持关闭倍率和 Embeddings 行为兼容。

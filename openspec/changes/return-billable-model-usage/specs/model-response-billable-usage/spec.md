## ADDED Requirements

### Requirement: 模型响应暴露计费用量
对于完整成功且上游用量可得的模型请求，系统 MUST 在标准 usage 中返回与计费记录一致的 token 用量，同时保留原始用量供内部审计。

#### Scenario: OpenAI 输入包含缓存
- **WHEN** 倍率为 2.5，上游输入为 100，其中缓存读取为 20，输出为 20
- **THEN** 响应输入为 220，输出为 50，总量为 270，缓存读取仍为 20
- **THEN** 计费记录采用相同的 billable 分类，原始用量不被响应改写污染

#### Scenario: Claude 按协议拆分用量
- **WHEN** 上游非缓存输入为 80，缓存读取为 20，输出为 20，倍率为 2.5
- **THEN** 标准 usage 的输入为 200，缓存读取为 20，输出为 50

#### Scenario: 流式或 WebSocket 请求
- **WHEN** 完整流或 WebSocket 单轮包含最终用量
- **THEN** 相应协议的最终 usage 与该轮计费用量一致，事件顺序与累计语义保持有效

### Requirement: 计量策略与结算一致
系统 MUST 对同一请求的响应与计费使用同一份计量策略，并按现有计费规则处理缓存、取整和多次上游调用。

#### Scenario: 请求期间倍率变更
- **WHEN** 请求进行期间管理员修改平台计量倍率
- **THEN** 该请求的响应与异步计费均采用同一份策略快照

#### Scenario: 未启用倍率或 Embeddings
- **WHEN** 计量放大关闭或请求按现有规则不应用该倍率
- **THEN** 标准 usage 使用该请求既有的计费用量，不额外放大

### Requirement: 不完整用量不伪装为最终账单
系统 MUST 保留缺失、异常和中断场景的真实可知边界，不得伪造完整计费用量或保证异步扣费成功。

#### Scenario: 上游没有最终 usage
- **WHEN** 上游没有返回完整最终 usage 或客户端在最终事件前断开
- **THEN** 系统不得将部分信息作为已确认的最终账单保证
